# Eduroam 第三方登录

## 学校账号后缀

进入管理端「Eduroam 认证 → 认证设置 → 学校账号配置」，在「学校账号后缀（认证域）」中填写 `@xx.edu.cn` 或 `xx.edu.cn` 并保存。

登录框会固定显示 `@xx.edu.cn`，用户只需填写学号 / 工号，例如 `20260001`，后端自动使用 `20260001@xx.edu.cn` 认证。用户粘贴同学校的完整账号也可以登录，不会重复追加后缀；其他学校域名会被拒绝。留空时不限学校，用户须填写完整账号。

已有「Eduroam 认证域」配置直接沿用，无需重新填写。「本站邮箱域」用于生成本站用户的邮箱和用户名，不用于自动补全校园认证账号。

## 首次开户与本站密码

从 1.2.0 起，校园认证成功且映射的本站邮箱尚无账号时，登录页自动进入「设置本站密码」。例如认证域为 `ysu.edu.cn`、本站邮箱域为 `stumail.ysu.edu.cn`，输入学号 `20260001` 后使用 `20260001@ysu.edu.cn` 认证，并以 `20260001@stumail.ysu.edu.cn` 为用户名和邮箱创建本站普通用户。本站邮箱域留空时沿用认证域。

用户必须输入并确认新的本站密码（至少 8 个字符，UTF-8 不超过 72 字节）。校园密码不会自动用作本站密码，插件不持久化任何明文密码；本站密码交给宿主用户服务编码保存，角色和部门沿用宿主普通用户默认值。新用户以校园认证作为身份核验，本站邮箱按管理员配置映射，不再另发激活邮件。

邮箱已有用户时不会改密或重复开户；已有其他本站账号的用户也可选择「已有本站账号，继续绑定」。首次创建后，当前已发布的宿主接口仍要求使用刚设置的密码登录一次完成绑定，后续 eduroam 登录沿用已建立的绑定。

开户接口只接受一次性校园认证票据、state 和新的本站密码，不接受客户端指定的邮箱、用户 ID 或角色。票据 5 分钟内有效；开户时重新检查通道开关、封禁状态和邮箱配置，过期、重放或配置已变更均须重新认证。后台用户服务故障不会被当作账号不存在。

宿主 SPI 2.29.0 的自动绑定扩展已在宿主源码中准备，尚须按契约发布流程发布并升级宿主，再由插件接入；未完成这些步骤前不能只靠替换此插件实现首次自动登录。

## 认证服务

从 1.1.1 起，默认认证服务为 [北京大学 Eduroam 探测点](https://analysis.eduroam.edu.cn/checkc/pkudetection)。管理端「Eduroam 登录设置」的认证服务地址填写该页面地址即可。

插件先读取页面获取独立会话的 Cookie 与 CSRF 令牌，再向同站 `/checkc/peapmschap` 提交 URL 编码的 `username`、`passwd` 和 CSRF 表单字段，使用页面默认的 PEAP/MSCHAPv2 协议。只有 JSON 顶层 `logtitle` 明确为 `"SUCCESS"` 或 `["SUCCESS"]` 才认证通过；1.1.3 修复了上游实际返回单元素数组时被误报为 JSON 异常的问题。包含多个状态的数组、页面不可用、缺少令牌、接口重定向或无效结果均拒绝认证。

认证请求中的密码和上游调试日志不进入新站点的审计摘要；审计只保存已识别的认证结果与失败分类。Cookie 和令牌仅在本次请求内使用，各次登录互不共享。

审计中的 `RADIUS Access-Reject` 表示上游明确拒绝认证，可检查学校认证域、账号及密码；它与响应为空、HTML 错误页面、JSON 格式或状态字段异常分别展示。旧版本的「未返回有效的 JSON 认证结果」无法区分上游认证成功与失败，应升级后重新验证。

## 从旧版本升级

- 原默认地址 `https://eduroam.ustc.edu.cn/cgi-bin/eduroam-test.cgi`（含 HTTP 写法）在读取已有配置时自动切换，无需手工清空数据库；下次保存设置会写入新地址。
- 认证域、入库邮箱域、登录绑定、限流与封禁规则保持原配置。
- 其他自定义地址仍使用原有 `login/password` 表单和 HTML 结果协议，升级不会覆盖这些地址。
- 未配置认证域时，用户须填写包含学校域名的完整 Eduroam 账号。

可运行模块的 Maven 测试验证会话、表单编码、错误响应和结果解析。真实账号的端到端登录仍需要使用本校有效账号在部署环境验证。
